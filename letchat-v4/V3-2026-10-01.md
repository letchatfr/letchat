# Letchat V3 — proposition du 1er octobre 2026

Cette branche prépare les sept améliorations demandées. Elle ne publie pas le site. La base de référence est `157f51ca0ce943d8d709fa6b3ff79f8ee8d23b11` ; l'application maintenue est `letchat-v4/`.

## Fonctionnalités

| Volet | Résultat |
| --- | --- |
| 1. Dépôt et déploiement | Application unique, imports historiques dans `archive/`, point d'entrée racine compatible, Blueprint Render unique ciblant l'application et la base existantes. |
| 2. Interface | Palette verte commune, une feuille CSS chargée pour le tchat, navigation vers les nouveaux outils, formulaires et fenêtres adaptés aux petits écrans. |
| 3. Messages et notifications | Correction de ses messages texte publics et privés avec détection des modifications concurrentes ; recherche dans le salon ou la conversation privée active ; préférences push et pause temporaire. |
| 4. Communautés | Découverte par thème, création, règles versionnées, adhésion explicite, messages conservés 48 heures, responsables, modérateurs, exclusions, transfert et archivage. Administration : pause et traitement des messages signalés. |
| 5. Rencontre Surprise | Choix texte ou vidéo, mise en relation avec une personne ayant choisi le même mode, invitation vidéo explicite et idées de conversation insérées comme brouillons. |
| 6. Diagnostic | Disponibilité de la base, erreurs et latence API, signaux techniques des appels et de l'interface, mémoire et version. Compteurs agrégés en mémoire, sans contenu des échanges ni identifiants de membres. |
| 7. Pages publiques | Un index de guides et quatre articles distincts : tchat gratuit, musique, cinéma/séries et Rencontre Surprise ; liens internes, titres, descriptions, canoniques et sitemap. |

Les recherches et corrections respectent les accès Premium, les blocages et l'expiration des messages. La modification ne prolonge pas les 48 heures de conservation. Les messages des groupes et des nouvelles communautés ne disposent pas de la correction/recherche de ce premier lot. Les préférences concernent les notifications push ; les notifications visibles dans le site restent accessibles.

La caméra ne démarre jamais au moment de la mise en relation Surprise. Le parcours utilise l'invitation et l'acceptation existantes. Quitter une rencontre termine son appel. Les statistiques techniques repartent de zéro au redémarrage et ne constituent pas un suivi permanent des incidents.

## Validation automatisée

Exécuter depuis `letchat-v4/` :

```sh
npm ci
npm run build
npm run check
npm test
npm run test:v3
npm run test:integration
npm run test:admin
npm run test:community
npm run test:surprise
npm run test:social
```

Les tests d'intégration utilisent une base temporaire PGlite, avec les services externes simulés. Ils couvrent les autorisations, les routes HTTP, les migrations, les événements Socket.IO, les blocages, la conservation des messages et les régressions des fonctions existantes. Les tests d'interface utilisent JSDOM : ils vérifient les formulaires et interactions sans rendre les pixels d'un navigateur. Le Blueprint est également validé contre le schéma officiel Render.

Deux régressions ont été corrigées pendant les contrôles : la route de correction des messages interceptait l'épinglage administrateur ; la pagination générique de l'administration écrasait celle des communautés. Les tests correspondants couvrent les corrections.

## Vérifications restant nécessaires avant publication

- Parcourir l'interface sur un vrai navigateur d'ordinateur et de téléphone : clavier ouvert, fenêtres, navigation, contraste et lisibilité. La prévisualisation locale depuis le navigateur de cette session a été bloquée ; aucune validation visuelle complète n'est revendiquée.
- Tester une rencontre vidéo entre deux appareils sur des réseaux différents, avec acceptation/refus, changement de partenaire et autorisations caméra/micro. La signalisation est testée automatiquement, pas la qualité réelle des flux ni du relais TURN.
- Vérifier les notifications push sur les appareils utilisés, les permissions, les préférences et la pause temporaire.
- Valider les migrations sur une copie de PostgreSQL et les verrous entre plusieurs processus. PGlite ne remplace pas ce contrôle de concurrence.
- Confirmer les réglages du service Render existant et vérifier `/api/ready` après un déploiement de préproduction. Aucun paiement réel ni aucune modification du service Render n'a été effectué pendant ce travail.

## Publication et retour arrière

1. Examiner la proposition, terminer les vérifications manuelles et conserver une sauvegarde de la base existante.
2. Vérifier le service Render actuel : dossier `letchat-v4`, construction `npm ci && npm run build`, lancement `npm start`. Conserver les clés, la base, le plan et les accès administrateurs déjà configurés. Une synchronisation du Blueprint n'est pas requise pour examiner cette proposition.
3. Après accord de publication, fusionner puis contrôler le déploiement et les parcours de connexion, messagerie, communauté et Surprise.
4. En cas de régression, redéployer le commit précédent. Les migrations sont additives : deux colonnes `edited_at`, les tables de communautés et les préférences de notifications. L'ancienne version ignore ces ajouts ; les fonctions V3 deviennent indisponibles et leurs données restent dans la base jusqu'à une intervention ultérieure.

Le Blueprint ne crée pas de base ni de nouveau plan. Les 99 fichiers historiques sont conservés dans `archive/versions-historiques.zip`, avec leurs chemins et leur contenu vérifiés octet par octet ; ils ne sont pas servis. La CI exécute les suites principales à chaque proposition touchant l'application ou sa configuration.
